# BDV Travel OS Agent Guide

This file is the source of truth for coding agents working in this repo. Keep it short and update it when the workflow changes.

## Project Map

- Frontend: `frontend/`, React via CRA/craco, deployed on Vercel.
- Backend: `backend/server.py`, FastAPI single-file app, deployed on Railway.
- Database: MongoDB via Motor. Supabase/Postgres is a future migration, not the current stack.
- Uploads: runtime files live under `backend/uploads/`. Do not add new uploads to git; existing tracked uploads are pending review.
- Architecture docs: `docs/*.html` generated by Archify, with `docs/README.md` as the index.

## Working Rules

- Start every task by reading this file, `README.md`, and any touched feature files.
- Use the existing single-file backend and existing frontend patterns unless the task explicitly asks for a refactor.
- Keep PRs focused. Do not mix governance/docs, security fixes, and product features in one PR.
- Never push directly to `main`. Work on a branch and open a PR.
- Do not commit secrets, `.env` files, uploaded documents, screenshots with client data, or generated local runtime data.
- If a change touches routing, auth, data shape, deployment, or shared state, include an architecture impact note in the PR.

## Verification

Run the smallest relevant check before handing off:

- Frontend build: `cd frontend && yarn build`
- Backend tests: `cd backend && python -m pytest`
- Do not change `backend/pytest.ini` addopts casually; it intentionally pins xdist to `-n 2 --dist loadscope`.
- Conflict-marker check: `rg -n "^(<<<<<<<|=======|>>>>>>>)" . -g '!frontend/yarn.lock' -g '!docs/*.html'`

If a check cannot run locally, say why in the PR.

## PR Expectations

Every PR should include:

- What changed.
- What was verified.
- Deployment impact for Vercel/Railway/env vars.
- Archify impact: which diagrams changed or "no architecture impact".
- PRLens review status before merge.
